# infra-ops workflow

## Source of truth

The CSVs in `infra-ops/inventory/` are the source of truth for all homelab
state. `hosts.yml` is generated by `scripts/csv-to-inventory.py`. Never edit
`hosts.yml` by hand. It gets overwritten by `make inventory`.

| CSV | Owns |
|---|---|
| `service-inventory.csv` | Every machine, VM, and LXC |
| `caddy-sites.csv` | Every public hostname and proxy entry |
| `databases.csv` | Per-project Postgres databases |
| `api-keys.csv` | Secret metadata only (no values) |

Run `make lint-inventory` before and after any CSV edit to catch schema
violations before they reach Ansible.

## Change sequence

1. Edit the relevant CSV.
2. Run `make diff-<thing>` to preview the change (read-only, no mutation).
3. Review the diff output.
4. Run `make deploy-<thing>` and confirm the interactive prompt.
5. Commit and push.

Every `deploy-*` target has a paired `diff-*`. Always run the diff first.
Do not run `make deploy-*` non-interactively. The read prompt will hang.

## Secrets

Secret values go in `vault.yml` only. `api-keys.csv` holds metadata (provider,
scope, vault entry name) and never the actual token or password.

Edit vault with: `make vault-edit` (decrypts, opens $EDITOR, re-encrypts).
View vault with: `make vault-view`.

The vault password is stored in macOS Keychain as `infra-ops-vault-password`
and resolved automatically by `scripts/vault-pass-keychain.sh`.

Never write secret values into CSVs, templates, playbook output, or commit
messages.

## New service sequence

For a service that is not yet in the Makefile:

```bash
make provision-lxc vmid=<id> name=<slug> ip=<ip>
make new-project name=<slug> image=<img:tag> port=<n> password=<pw>
```

Order matters. Provision creates the LXC and installs Docker. Deploy renders
the compose template and starts the service. Running deploy before provision
will fail.

For services that already have a Makefile target: start at step 1 of the
change sequence above.

## State vs. intent during migrations

If the actual state of a host diverges from a CSV entry mid-migration, set
the CSV to match reality and record the intended final state in `migrations.md`.
Do not set the CSV to the desired future state and leave reality behind. The
CSV describes what is, not what will be.

## After changes

Commit and push to Gitea. The Gitea repo is the source of truth for the
control plane. Changes that exist only on the local machine are not backed up
and are not visible to other contexts.
